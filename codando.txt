7. Rodapé: "Cancelar" e "Confirmar"

### Bloco do Starter (item 6)

Design: cliente quer os dois botões IGUAIS, sem destaque entre eles.

Visual:
```
┌────────────────────────────────────────┐
│ Teve pedido nessa visita?              │
│ ┌────────────────────────────────────┐ │
│ │ Valor                              │ │
│ │ R$ [_________]                     │ │
│ │                                    │ │
│ │ [Salvar como pedido]               │ │
│ │ [Salvar como orçamento]            │ │
│ └────────────────────────────────────┘ │
│ Deixe em branco se não houve pedido.   │
│ Check-in será salvo sem pedido.        │
└────────────────────────────────────────┘
```

Ambos botões: mesma borda neutra, sem destaque azul.

### Edge case do Starter: valor preenchido sem escolher tipo

Regra aprovada: bloqueia "Confirmar" do rodapé.

Implementação:
- Se `valor > 0` E `tipoPedido == null` → botão "Confirmar" do 
  rodapé fica disabled
- Mostra hint inline abaixo do bloco: "Escolha se é pedido ou 
  orçamento, ou limpe o valor para salvar apenas o check-in."
- Se `valor == 0 ou vazio` → tipoPedido ignorado, "Confirmar" 
  funciona normalmente (salva só visita)

### Bloco do Pro/Enterprise (item 6)

NÃO RENDERIZA. Pula direto de "Registrar gasto?" pros botões 
"Cancelar/Confirmar".

Ler plano via hook existente (usePlano ou similar — usar o mesmo 
padrão que CheckinLegacy usa hoje).

## Lógica de salvamento

### Passo 1 — INSERT em `visitas`

```js
const { data: visita, error } = await supabase
  .from('visitas')
  .insert({
    cliente_id: clienteId,       // via useParams
    rep_id: repId,                // via getRepId()
    tipo: tipoVisita,             // 'presencial' ou 'whatsapp'
    observacao: observacao || null,
    data: hojeBR(),               // ver regra no passo 4
    // criado_em, registrado_em: default now()
  })
  .select()
  .single()
```

IMPORTANTE: verificar no schema atual quais colunas `visitas` 
realmente tem. Memórias indicam que tem: id (bigint), cliente_id, 
rep_id, tipo, observacao, data (DATE), criado_em (timestamptz), 
registrado_em (timestamptz). Confirme antes de fazer o insert.

Se der erro: mostra toast "Erro ao salvar check-in" e PARA.

### Passo 2 (SÓ SE Starter E valor > 0 E tipoPedido escolhido)

INSERT em `pedidos`:

```js
await supabase.from('pedidos').insert({
  cliente_id: clienteId,
  rep_id: repId,
  visita_id: visita.id,           // ← FK nova da Etapa 1
  valor_total: valorDigitado,
  status_empresa: 'aprovado',     // pedido simples Starter já 
                                   // nasce aprovado — trigger 
                                   // preenche aprovado_em
  status: tipoPedido,             // 'pedido' ou 'orcamento'
  // demais campos default
})
```

IMPORTANTE: confirmar no código existente (PedidoSimples.jsx?) 
qual o padrão de campos que um pedido simples do Starter tem hoje. 
Usar o MESMO padrão — não inventar campos novos.

Se erro: toast "Check-in salvo, mas pedido falhou. Tente pelo Novo 
Pedido" + continua pro passo 3 (NÃO rollback da visita).

### Passo 3 (se gasto foi adicionado)

Verificar se `gastos_cliente` tem coluna `visita_id`. Se tiver: 
preencher com visita.id. Se não tiver: só salvar o gasto sem vínculo.

### Passo 4 — UPDATE em `clientes.ultima_visita`

REGRA CRÍTICA (documentada no CLAUDE.md): ultima_visita só atualiza 
em visita PRESENCIAL. WhatsApp NÃO atualiza.

```js
if (tipoVisita === 'presencial') {
  await supabase
    .from('clientes')
    .update({ ultima_visita: hojeBR() })
    .eq('id', clienteId)
}
```

### Passo 5 — navigate(`/clientes/${clienteId}`)

### Timeouts

Usar Promise.race com 10s em cada query (padrão CLAUDE.md):

```js
await Promise.race([
  supabase.from('...').insert(...),
  new Promise((_, reject) => setTimeout(() => reject(new Error('timeout')), 10000))
])
```

## Helper de data

Verifique se o v2 já tem um helper de data BR. Se não, importe 
`hojeBR` do SalesRP (se existir compartilhamento) ou crie um mínimo 
inline usando:

```js
const hojeBR = () => new Intl.DateTimeFormat('en-CA', {
  timeZone: 'America/Sao_Paulo',
  year: 'numeric', month: '2-digit', day: '2-digit'
}).format(new Date())
```

NÃO use `new Date().toISOString().split('T')[0]` — esse é o bug que 
estamos eliminando.

## Testes manuais OBRIGATÓRIOS antes do commit

Acesse diretamente pela URL `/clientes/<algum-id-real>/checkin`. 
Teste 8 cenários:

1. Starter, tipo=Presencial, sem obs, sem pedido, sem gasto 
   → INSERT visitas, UPDATE ultima_visita, redirect OK

2. Starter, tipo=WhatsApp, com obs, sem pedido 
   → INSERT visitas, ultima_visita NÃO atualiza, redirect OK

3. Starter, tipo=Presencial, valor R$ 100, botão "Salvar como pedido" 
   → INSERT visitas + INSERT pedidos (visita_id preenchida, 
   status='pedido', valor_total=100)

4. Starter, tipo=Presencial, valor R$ 100, botão "Salvar como orçamento" 
   → INSERT visitas + INSERT pedidos (status='orcamento')

5. Starter, valor preenchido mas NÃO escolheu tipo → "Confirmar" 
   disabled + hint visível

6. Starter, valor vazio, clica "Confirmar" → salva só visita 
   (ignora tipoPedido)

7. Pro/Enterprise, tipo=Presencial → seção de pedido NÃO aparece, 
   salva só visita

8. Sem tipo de visita selecionado, clica "Confirmar" → validação 
   "Escolha um tipo de visita"

Validação SQL depois dos testes 3 e 4:
```sql
SELECT id, cliente_id, visita_id, valor_total, status, status_empresa
FROM pedidos
WHERE visita_id IS NOT NULL
ORDER BY criado_em DESC LIMIT 5;
```

visita_id deve estar preenchido, apontando pra visita correta.
